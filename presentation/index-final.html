A primeira camada

Constitution

O que continua valendo quando a tarefa muda.

Princípios→Valores→Trade-offs→Limites

Não é tutorial. Não é checklist. É a orientação que ajuda o agente a decidir.

Pietro · exemplo concreto

Constitution não diz o que fazer. Diz como decidir.

Bom

Regra real de decisão

“Preferimos soluções simples e observáveis.
Complexidade precisa comprar uma capacidade clara.”

Se o agente propuser três componentes novos, ele precisa justificar a complexidade.

Ruim

Passo a passo disfarçado

“Use Spring Boot.
Crie controller.
Crie service.
Rode o build.”

Isso descreve execução, não um princípio que possa orientar decisões diferentes.

pietro-apontando.png
A segunda camada

Instructions

Padrões, convenções, regras e restrições para o trabalho cotidiano.

Se a Constitution responde “o que valorizamos?”, Instructions respondem “quais regras seguimos enquanto trabalhamos?”
Pietro · exemplo concreto

Instruction aparece no trabalho do agente.

Bom

Regra aplicável

“Toda chamada a API externa deve
ter timeout explícito, tratamento de
erro e métricas de latência.”

O agente pode aplicar a regra em qualquer integração nova.

Ruim

Conhecimento sem instrução

“Timeouts são importantes.”

É verdadeiro, mas não define o comportamento esperado.

pietro-explicando.png
A terceira camada

Skills

Conhecimento transformado em procedimento reutilizável.

Conhecimento→Procedimento→Execução

Uma skill evita que cada agente invente novamente o caminho para uma atividade recorrente.

Pietro · exemplo concreto

Skill é um caminho executável.

Bom

Skill de integração

Entrada: endpoint + contrato
1. Criar cliente
2. Configurar timeout
3. Retry / rate limit
4. Instrumentar métricas
5. Criar testes
Saída: integração validada
Ruim

Pedido genérico

“Faça uma integração com a API.”

Cada agente decide seu próprio processo. O resultado varia entre projetos.

pietro-demonstrando.png
A quarta camada

Context

O mundo real onde a missão acontece.

Produto→Sistema→Arquitetura→Cadastro→Usuário

Contexto reduz a necessidade de o agente descobrir sozinho onde está pisando.

Pietro · exemplo concreto

Context não é “mais texto”. É informação relevante para a decisão.

Bom

Contexto do nosso cadastro

Produto: app bancário
Regra: CPF único
Identidade: já existe
Compatibilidade: clientes atuais
Restrição: não quebrar jornada existente
Ruim

Contexto insuficiente

“Crie um CRUD de usuário.”

O agente sabe o recurso, mas não sabe o sistema, as regras nem as consequências.

pietro-mostrando-mapa.png
A quinta camada

Mission

O contrato de execução: Contexto + Objetivo + Restrições + Critérios de aceite.

Uma boa missão pede um resultado verificável sem precisar coreografar cada tecla.
Pietro · exemplo concreto

Mission define o que precisa estar pronto.

Bom

Missão verificável

Objetivo: implementar cadastro de usuários.
Restrição: preservar compatibilidade.
Aceite:
✓ CPF único
✓ testes de integração
✓ pipeline verde

O agente escolhe a implementação, mas não escolhe o que significa “pronto”.

Ruim

Prompt coreografado

“Abra UserController.java.
Adicione o método X.
Depois rode o comando Y.
Depois altere o arquivo Z...”

O humano vira operador remoto do agente.

Decomposição

Responsabilidade antes de personalidade.

Objetivo → Resultados → Responsabilidades → Dependências → Missões → Evidências

Delegar é distribuir contexto, responsabilidade e critérios de sucesso.

O mesmo cadastro, agora decomposto

Uma missão vira várias missões menores.

Produto

Definir quem pode criar usuário e qual jornada precisa ser preservada.

Segurança

Validar autenticação, autorização e proteção do CPF.

Arquitetura

Mapear integração com identidade existente e impacto nos clientes.

Testes

Definir cenários de aceite e evidências necessárias.

Paralelismo

Nem tudo precisa ser paralelo.

descoberta
 ├─→ produto
 ├─→ segurança
 ├─→ testes
 └─→ arquitetura
          ↓
     decisão arquitetural
          ↓
      implementação
       ├─→ testes
       └─→ revisão
          ↓
       integração

Paralelizar cedo demais também cria retrabalho.
